# Roadmap

Each phase must leave the app runnable. Do not start a phase without explicit authorization.

| # | Phase | Status | Summary |
|---|---|---|---|
| 1 | Foundation | **Complete** (commit `9d62d2e`) | Electron shell, secure preload and typed IPC, SQLite + Drizzle migrations, dashboard, project registration and persistence |
| 2 | Project workspace, onboarding, Team Lead chat | **Complete** (merged into `main`) (verification caveats below) | Project page, onboarding lifecycle, discovery of CLAUDE.md and `.claude/`, Team Lead via Claude Agent SDK, session persistence and resume, streaming chat |
| 3 | Tasks and orchestration | **Complete** (commit `7806cd5`; caveats below) | Task model, backlog UI, dependencies, validated state machine, Team Lead task tools (propose, user approves), persistent event history |
| 4 | Developer agent runtime | **Implemented** (commit `a18cf97`; caveats below) | Claude Code CLI in node-pty, git worktrees, xterm.js terminals, agent persistence |
| 5 | Planning and approval | **Implemented** (commit `8fee9c3`; caveats below) | Plan capture and versioning, Team Lead review (advice), user approval records, backend-enforced execution gate |
| 6 | Execution and review | **Implemented** (commit `b8ad426`; caveats below) | Gated execution, agent reports as claims plus Orbyte-collected git evidence, Team Lead result review (advice), user acceptance as the only completion path, change requests |
| 7 | Reliability and polish | **Implemented, packaging deferred** (commit `3b17711`; caveats below) | File logging, startup recovery sweep, orphan cleanup, database backup, two Phase 6 gaps closed. Packaging is **Planned** (deferred by decision: no builds for now) |

## Phase 1 acceptance (met, with caveats)
App launches; project registered by token flow and persisted (tested at service/DB level); renderer isolated (verified over DevTools protocol). Caveat: the native folder dialog was not exercised end-to-end.

## Phase 2 acceptance
Verified by running the built app with the real SDK and the user's existing Claude Code login (project row seeded into a throwaway user-data directory, because the native folder dialog cannot be driven over the DevTools protocol): onboarding reached `ready` with discovery, summary and guidance; chat streamed; an edit request was refused and no file was created; after an app restart the session id and history persisted and the follow-up turn resumed the same session; archive/restore and input validation behaved as specified; the renderer stayed isolated. 71 automated tests pass (the real SDK is not used in automated tests). A follow-up security review's findings were fixed or documented (see `SECURITY.md`); the trust gate was verified with real UI clicks and real SDK turns in both trust modes.

Not verified: the native folder dialog; the quit path in a running app; visual UI quality (the project route was only checked to render); a not-signed-in run (auth error mapping is heuristic); a packaged build; resuming after the SDK's session file is deleted (covered by a fake-runner test and by observing the SDK's error text for a bogus id).

## Phase 3 acceptance
Verified with 140 automated tests, a read-only security review (findings fixed or recorded in `SECURITY.md`), and a real run (built app, real SDK): tasks persist; dependencies are validated (self, cycle, missing, other project); every illegal user transition is refused and the allowed set is exhaustively tested; the Team Lead's propose tool recorded a proposal and created no task; approving a subset with an edited title created exactly those tasks with provenance and dependencies; approving twice or from another project was refused; a plain question produced no proposal; activity history, the dashboard "Open tasks" count and the Tasks tab (including proposal review) work.

Not verified: the visual quality of the Tasks UI (checked that it renders the expected text, not how it looks); behavior with large backlogs (the Team Lead digest is capped at 100 tasks); the "orchestrator" actor paths beyond unit tests (no caller exists until Phase 4). Phase 3 has no separate orchestrator process: `TaskService` plus the state machine is the orchestrator for task state, and the execution workflow arrives in Phases 4-6.

## Phase 4 acceptance
Verified with 211 automated tests (real git and database, fake PTY) and a real run in the built app (real `node-pty`, real `claude`, scratch repository): starting an agent for a Ready task created an isolated worktree and branch, moved the task to planning and started a real `claude` process with the planned flags (found with `ps`); the user's own working tree stayed clean; terminal output streamed to the renderer, resize and write validation worked, the agent's terminal title appeared as its activity, and the Agents tab rendered the agent with an xterm terminal; blocking the task stopped the agent and the block stood; the saved history replayed after exit; discard removed the worktree and the unmoved branch; after a hard kill of the app the agent was marked interrupted, its task was Ready again, and no process or branch was left behind. A read-only security review of this phase found no critical issues and one high (archiving did not stop agents), five medium (a shutdown race, discard silently losing detached-HEAD commits, uncaught errors in PTY callbacks, replayed terminal queries typed into the session, and a tool denylist that left ~55 tools) and several low items; all but the documented gaps in `SECURITY.md` were fixed and tested, and the new launch flags and the archive fix were re-verified against the real CLI and a live agent.

Findings that shaped the design: deny rules hold even after cycling out of plan mode, but Claude Code's `!` shell mode still runs commands (the model is restricted, a person typing is not); Claude shows its own folder-trust prompt in new worktrees; `CLAUDE_*` environment markers can switch off transcript saving.

Not verified: real keyboard typing in the xterm UI (input was tested through the IPC write path); how the Agents tab looks; macOS only; very large or long-running output; resuming an agent's session (the session id is recorded for Phase 5/6); plan capture and the approval gate (Phase 5).

## Phase 5 acceptance
Verified with 270 automated tests, a read-only security review (no forging path found; its findings fixed or recorded in `SECURITY.md`), and a real run in the built app with the real agent and the real Team Lead: the agent investigated and submitted a structured plan through the real MCP tool (steps, files, tests, risks); it was stored as version 1 and the task moved to `awaiting_approval`; the Team Lead reviewed it automatically (advice recorded, no approval created, gate still closed); a made-up plan id and a wrong project were refused; my approval created a record with the right agent, version and hash and opened the gate; approving twice was refused; revoking closed it; the audit trail recorded submission, review, approval and invalidation; the renderer has no channel to authorize execution; a second review used a one-shot session that left the chat session id and the saved session files unchanged.

Findings that shaped the design: in this CLI version `ExitPlanMode` carries no plan text in its hook input, so Orbyte provides its own `submit_plan` tool; plan mode asks permission for MCP tools unless they are declared read-only, and Orbyte must not answer prompts for you; Orbyte cannot see the plan unless the agent calls the tool.

Not verified: a real reject-then-revise loop with a live agent (covered by tests with fake processes); how the plan dialog looks (checked that it renders the expected text); behavior when the Team Lead is busy for a long time (covered by a test with a stub); packaging of the plan server; approval integrity against a local process running as you (open design question, see `SECURITY.md`). Execution is not built: the gate can authorize it and nothing launches it.

## Phase 6 acceptance
Verified with 281 automated tests (real git and database, fake PTY), a read-only security review (no way found to start or complete a task without your stored decision; its findings were fixed or recorded in `SECURITY.md`, and the fixes have regression tests), and a real run in the built app (real `claude` agent, real Team Lead, scratch repository): the planning agent's plan was reviewed and approved by me; `executions:start` before approval was refused and a second start after the approval was spent was refused; the execution agent edited `math.js` in its worktree and called `submit_result`; Orbyte collected the evidence itself (one changed file, +1 line, uncommitted, no commits) and the task moved to `in_review`; the Team Lead reviewed the result automatically (advice only); a direct move to `completed` was refused; editing the worktree after review made `accept` fail with `CODE_CHANGED`; `accept` from another project id got `NOT_FOUND`; `requestChanges` started a revision run (a second request was refused), the new result superseded the first, accepting the old one got `STALE_RESULT` and the new one `REVIEW_REQUIRED` until the Team Lead had reviewed it; my acceptance then completed the task and the first decision showed as invalidated. The scratch repository's own working tree stayed clean and no agent or app process was left behind.

Findings that shaped the design: a pre-approved `git diff:*` prefix rule would have let an agent write or read files anywhere (flags are not parsed), so no Bash prefix is pre-approved; the agent can edit the worktree's `.git` pointer, so evidence collection refuses a worktree whose pointer no longer leads outside it; Claude asked for folder trust again in the new worktree (answered through `agents.write`).

Not verified: a result with no changes; very large diffs (the truncated path is refused by design but only covered by reasoning); approval and acceptance integrity against a local process running as you (deferred by decision, see `SECURITY.md`). Merging the agent's branch is left to you: Orbyte does not commit or merge.

## Phase 7 acceptance
Verified with 298 automated tests (logger redaction, sanitizing and rotation, the sweep, orphan scan and clean with real git worktrees, backup, the discard races, review binding) and a live run in the built app: the log file was created under `userData/logs` (mode 600, directory 700); at startup the sweep removed a stray inbox directory, reported two orphan worktrees in one audited `recovery.completed` event, and the renderer received no filesystem paths; cleaning a made-up id did nothing, cleaning the real orphans removed the clean one and kept the one with uncommitted work, and an empty id list was refused.

Scope decisions: packaging is not done by decision (no builds for now; `asarUnpack` for the SDK binary, `node-pty` and the agent server, and Electron Fuses remain **Planned**); the logger is a small file logger with levels, secret redaction and size rotation, not a dependency.

Not verified: the native save dialog for the database backup (the backup itself is tested through the service with a real database); the log's behavior on a full disk; a packaged build. A live kill during an execution was checked afterwards (see the follow-up check below).

## Follow-up live check (after Phase 7)
Run in the built app with a real `claude` agent and the real Team Lead against a scratch repository, with screenshots of the real UI: the dashboard, Maintenance panel, project tabs, plan dialog (Approve and Reject are reachable by scrolling inside the dialog) and result dialog (the agent's claim labelled unverified, git evidence labelled collected by Orbyte, Team Lead's output labelled advice) render correctly; Approve and Start execution were clicked in the UI. An execution agent hit a real Bash permission prompt (`node -e ...`); Orbyte did not answer it and the agent waited until a person did. Then a revision run was started and the Electron main process was killed with `kill -9`: the agent process did not survive, and on relaunch the startup recovery logged one interrupted agent and one interrupted run, the task returned to `awaiting_approval`, the worktree and the agent's file were kept, and `executions.start` was refused (`EXECUTION_NOT_AUTHORIZED`) until a new approval. Agent start now re-validates the project folder (`GitWorktrees.verifyRepo`).

Observed limitation: for a new, untracked file the evidence lists the file but its line counts and diff are empty, so the Team Lead read the file itself. Not fixed.

## Open items after Phase 7
Deciding whether approval and acceptance rows need signing; `repoPath` re-validation for the Team Lead and later worktree operations (agent start now re-validates); how to treat the `!` shell-mode gap; an Orbyte-run test command (not built by decision); packaging (**Planned**, deferred): `asarUnpack` for the SDK binary, `node-pty` and the agent server, Electron Fuses, signing.
