# Security

Distinguishes what the **code enforces** from what is only an **instruction** to AI tools. Do not describe an instruction as enforcement.
Last reviewed: Phase 1 security review (read-only agent review plus grep sweep). No critical or high findings.

## Code-enforced today (Implemented)
- `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`, `webSecurity: true`, `webviewTag: false` (`src/main/app/window.ts`). `require`, `process` and `window.electron` being undefined in the renderer was checked **manually** over the DevTools protocol (built and dev modes); no automated test covers it.
- Narrow preload: only `window.orbyte.{projects,onboarding,teamLead,onEvent}` with fixed methods; no `ipcRenderer`. Incoming push events are re-validated with Zod in the preload and malformed ones are dropped.
- All handlers go through `handle()`: **IPC sender check** (only the top-level frame of the app's own page; fails closed until the app entry is set; `isTrustedFrame` is unit-tested as a pure function), Zod validation, errors mapped to `Result`. Unexpected errors reach the renderer only as a generic `INTERNAL` message; full errors are logged in main.
- No renderer-supplied paths: directories are picked in main and registered by single-use token (10-minute TTL, in memory, at most 20 pending, oldest evicted). Only one directory selection at a time (`DIALOG_BUSY`). Path is re-validated at registration (`realpath` + `isDirectory`).
- Input limits: `token`/`id`/`projectId` at most 64 characters; chat messages 1-20,000 characters.
- App-wide guards on **every** web contents (`src/main/app/security.ts`, registered before any window): navigation, redirect and frame navigation are prevented unless the URL is the app's own entry; webviews are prevented; `window.open` is denied; only well-formed `https:` URLs without credentials open externally. Rules are in `app/navigation-policy.ts` (unit-tested). Deny-all permission handlers on the default session.
- Git runs through `execFile` with an argument array, no shell, 10-second timeout, `-c core.fsmonitor=false`, `GIT_OPTIONAL_LOCKS=0`, `GIT_TERMINAL_PROMPT=0`. Commands used (`rev-parse`, `symbolic-ref`) are read-only.
- CSP is injected at build time (`electron.vite.config.ts`). Production: `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self'; object-src 'none'; base-uri 'none'; form-action 'none'`. The dev server gets a looser CSP that is not in built output.
- Single-instance lock. SQL goes through Drizzle (parameterized); `foreign_keys = ON`; `repo_path` is unique.
- **Team Lead is read-only by construction** (`src/main/modules/agents/team-lead/options.ts`, asserted by tests): `tools: [Read, Glob, Grep]`, `disallowedTools` includes `Edit, Write, NotebookEdit, Bash` (plus `mcp__*` when no task tools are enabled), `strictMcpConfig: true`, `permissionMode: 'dontAsk'`. `allowedTools` is set only for chat turns and is exactly Orbyte's two in-process tools (`mcp__orbyte__list_tasks`, `mcp__orbyte__propose_tasks`); `mcp__*` is dropped then because it works as a wildcard and also blocked our own tools in testing (without `allowedTools` the tool is listed but cannot run under `dontAsk`). Verified against the real SDK: the init message listed exactly `Glob, Grep, Read`, and an edit request was refused with no file created. This is SDK-enforced tool removal, not a prompt rule.
- Discovery (`modules/projects/discovery.ts`) is read-only and bounded (depth 3, 400 dirs, 25 CLAUDE.md files); it never follows symlinks out of the repo and never writes. Onboarding output is stored in Orbyte's database only, never in the repository.
- **Team Lead failure handling:** one turn per project; turns time out after 15 minutes (`TIMEOUT`) and chat turns are capped at 40 agent turns; `runTurn` never rejects (failures become `turn_error` and free the turn slot); a throwing event emit cannot break a turn; chat is refused while onboarding runs; refused turns emit no events; raw SDK/runtime error text is logged in main only and the renderer receives fixed messages per error code; the main process logs unhandled rejections, shows an error dialog and exits if startup fails, and on quit aborts in-flight turns (waiting up to 3 seconds) before closing the database.
- **Task creation is human-authorized in code:** the Team Lead's `propose_tasks` can only record a proposal; creating tasks happens only in `ProposalService.approve`, called from the renderer's approve action and checked for project ownership, pending status and dependencies, atomically. Tool input is Zod-validated, size-limited and rate-limited (3 calls per turn, 5 pending proposals); the project id is bound server-side and the model cannot choose it. Onboarding turns get no task tools. Tested with unit tests and a real run (the Team Lead proposed, the task count stayed unchanged, and tasks appeared only after approval).
- **Task state machine** (`src/shared/task-state.ts`, default-deny, exhaustively tested): the renderer can only act as `user`; users cannot plan, start, review or complete tasks; `in_progress` can only be entered from `awaiting_approval` with `approvalVerified: true`, which nothing sets yet, so execution cannot start until Phase 5 supplies a real approval check. Moves are compare-and-set on the current status.
- **Task isolation:** every task, proposal and activity call carries a project id and is checked against the record's project; a task or proposal in another project gets the same `NOT_FOUND` as a missing one, and dependencies on other projects' tasks get the same message as missing ones.
- Team Lead and chat output is rendered as plain text (no HTML or markdown rendering), because it is untrusted.

## Team Lead trust model (read this before registering a repository)
- **Repo settings are opt-in per project.** Each project has `repoSettingsTrust`: `unset` (default), `trusted`, or `untrusted`. While `unset`, the Team Lead and onboarding are refused (`TRUST_REQUIRED`), enforced in main (`TeamLeadService`, `OnboardingService`) and mirrored in the UI. `trusted` loads user + project + local settings (what you chose), so the repo's hooks and settings run as they would if you ran `claude` there. `untrusted` loads user settings only. The prompt lists what the repo would bring (CLAUDE.md count, `.claude/`, and risky settings keys: `hooks`, `env`, `apiKeyHelper`, `statusLine`, `enabledPlugins`, `permissions`; names only). Existing projects upgrade to `unset`.
- **When trusted, hooks inherit Orbyte's full environment** (`env: {...process.env}`), including `ANTHROPIC_API_KEY` if set. That is the cost of trusting a repo; trust only repositories you own or have reviewed. When untrusted, only your own user-level hooks can run.
- **User-level settings, skills and plugins always load** (about 30 skills in testing), so behavior can differ per machine. Tools stay read-only regardless.
- **Without `strictMcpConfig` your personal MCP tools (including write-capable ones) were available to the Team Lead** in testing, even with `tools` restricted. `strictMcpConfig` plus `mcp__*` in `disallowedTools` removes them (verified: the tool list is exactly `Glob, Grep, Read`, and `mcp__*` does work as a wildcard). Do not drop either.
- **Read containment was tested, on this machine only.** With the exact Team Lead options and this machine's user settings, `Read` of a symlink to a file outside the repo, of a symlinked directory, and of an absolute path outside the repo were all denied (`dontAsk`), while an inside file read worked; a canary string in the outside file never leaked. A user-level `permissions.allow` or `additionalDirectories` rule on another machine could widen this; Orbyte does not enforce containment itself.
- **Authentication uses your existing Claude Code login** (`apiKeySource: none` in testing). The SDK docs say third-party apps should use an API key (or Bedrock/Vertex) and that Anthropic does not allow third parties to offer claude.ai login without approval. This app is personal and local, and the choice is yours; revisit before distributing it. `ANTHROPIC_API_KEY` in the environment is the documented alternative and needs no code change.
- The Team Lead can **read any file inside the project directory, including secrets such as `.env`**, and file contents are sent to Anthropic as part of the conversation. There is no path filter. Chat and onboarding text (which may contain such content) is stored unencrypted in `orbyte.db`.
- Prompt injection from repository content is possible; impact is limited because there are no write or execute tools. Discovery names placed in the onboarding prompt are sanitized (character set, length, count), which neutralizes structure (newlines, punctuation) but cannot remove plain instruction-like words. Treat output as untrusted.

## Known gaps (Limitation)
1. `style-src 'unsafe-inline'` remains in the production CSP (inline style attributes from UI components).
2. `name` and `description` are stored unsanitized: safe in React, but untrusted if ever placed into prompts.
3. `git` is resolved from `PATH` with the inherited environment.
4. `repoPath` is validated at registration and again before each developer agent starts (`GitWorktrees.verifyRepo`: it must still equal its own realpath, so a symlink swap is caught, and be a git work tree). Later worktree operations (discard, cleanup, evidence) and the Team Lead's per-turn reads do not re-validate it.
5. Auth failure detection is heuristic (matches error text, `AUTH_REQUIRED`); real not-signed-in behavior has not been exercised. The "session not found" fallback matches the SDK's current error text, observed but undocumented.
6. Electron Fuses are not configured: the agent helper (`agent-server.js`) runs as `ELECTRON_RUN_AS_NODE`, so the RunAsNode fuse cannot be turned off until that helper ships differently. Release builds are **unsigned and not notarized** (no Apple Developer ID); macOS shows a Gatekeeper warning. `electron-builder.yml` exists (see `DEVELOPMENT.md`, Releases).
7. No per-project ownership checks beyond id lookup exist because no per-project resource other than the project itself exists yet; they are required for tasks, agents and terminals.
8. Smaller, not fixed: `teamLeadSessionId` is sent to the renderer though unused; `onboardingData` is not validated on read; events are broadcast to all windows (fine for one window); `useTeamLeadChat` does not reset when `projectId` changes (not reachable today, the route remounts); a resume fallback silently loses model context while chat history still shows old messages; an in-progress turn's partial text is not replayed if you leave and return to the page.
9. Not covered by automated tests: window/webPreferences options, `installAppSecurity` wiring, CSP output, a real untrusted-frame IPC call (tested only as a pure function; subframes do not receive the preload API), the real SDK (tests use a fake runner; it was exercised manually), and the quit path (`before-quit` wiring was not exercised in a running app; `TeamLeadService.shutdown` is unit-tested). The native folder dialog and visual UI polish were not verified.
10. The database would still cascade `chat_messages` and `activity_events` if a project row were deleted directly (the app never does; it archives).

## Developer agents (Phase 4): what is and is not enforced
**Code-enforced**
- An agent is the user's real `claude` CLI started **directly** in a PTY with a fixed argument array (`modules/agents/developers/launch.ts`); there is no shell, and the renderer never supplies a command, path or executable. The binary is found by `resolveClaudeBinary` (PATH plus common install directories, no shell).
- **Isolated worktree per agent:** `userData/worktrees/<projectId>/<agentId>`, on a new `orbyte/<slug>-<id>` branch created at the default branch's commit. The user's own working tree is not touched (tested). Branch names must match `orbyte/<lowercase slug>`; removal only happens inside Orbyte's worktree directory; a worktree with changes is not removed unless the user forces it, nor one whose HEAD has commits that are on neither the branch nor the base (for example from a detached HEAD); containment follows symlinks, so a link swapped into the worktree path is refused; a directory deleted by hand is pruned and cleaned up; a branch is deleted atomically (`update-ref -d` with the expected commit) and only if it never moved from its base commit, so agent commits are never lost. **Known gap:** `git status` ignores ignored files (for example a `.env` or build output), and removing a worktree without force deletes them without warning.
- **Git is hardened for these commands:** hooks are disabled (a `post-checkout` hook would otherwise run code on `worktree add`; verified by a test that proves plain git runs it and Orbyte's runner does not), no fsmonitor, no prompts, an option-like ref cannot be smuggled in (`--end-of-options`).
- **Planning-stage launch:** `--permission-mode plan`, a known `--session-id`, a built-in **tool allowlist** `--tools=Read,Glob,Grep`, `--strict-mcp-config` (no MCP server starts), and an explicit deny list (`Edit, Write, NotebookEdit, Bash, WebFetch, WebSearch, Task, mcp__*`). Verified against the real CLI in both print mode and the live agent process: the tool list is exactly `Glob, Grep, Read` with no MCP servers. **An earlier version of this launch denied only four tools and left the agent about 55 (your personal MCP tools, subagents, web search, scheduling, worktrees); the Phase 4 review caught this and it was confirmed empirically before being fixed.** After cycling the mode to "accept edits", the CLI still refused `Write` and `Bash` for the model. Never uses bypass or accept-edits flags (tested).
- **Environment allowlist:** a list of names (PATH/HOME/USER/locale basics and an exact list of Claude Code settings) plus the `ANTHROPIC_` and `LC_` **prefixes**, so `ANTHROPIC_API_KEY`, `ANTHROPIC_BASE_URL` and similar pass through to the CLI (they are the user's own, and `ANTHROPIC_BASE_URL` can redirect traffic). The Claude Code settings in the list are (`CLAUDE_CONFIG_DIR`, `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_CODE_USE_BEDROCK|VERTEX|FOUNDRY|ANTHROPIC_AWS`). Other secrets in Orbyte's environment (cloud keys, tokens) are not passed. A broader `CLAUDE_` prefix was found to pass `CLAUDE_CODE_CHILD_SESSION`, which makes the agent think it is nested and switches off transcript saving, so it is not used. AWS/GCP credentials are not passed (Bedrock/Vertex users would need to extend the list).
- **Gating:** repo-settings trust must be decided (`unset` refuses; `untrusted` adds `--setting-sources user`); the project must be a git repo with a commit; the task must be Ready with all dependencies **completed** (so today only dependency-free tasks can start); one live agent per task (also a database unique index); at most 6 live agents; unknown/other-project/archived ids are refused.
- **Project scoping:** every agent call (list, stop, discard, attach, detach, write, resize) checks the agent's project; another project's agent gets the same `NOT_FOUND` as a missing one.
- **Terminal scoping:** output goes only to windows that attached to that agent (`TerminalHub`, window id taken from the IPC event, never from the renderer); writes are limited to 64 KB and resizes to 20-500 columns and 5-200 rows; both require a running agent.
- **Lifecycle:** stopping sends SIGTERM then SIGKILL after a grace period; cancelling or blocking a task in the UI stops its agent, and that decision is never undone (a task only returns to Ready if still in planning); **archiving a project stops its agents**, and the task is still returned to Ready (orchestrator bookkeeping works on archived projects, user moves do not); quitting stops every agent, and a start that is in flight during quit aborts before spawning (a closing flag, re-checked after git work); the output, exit and kill-timer callbacks catch their own errors, so a locked database cannot throw into the PTY or strand an agent in `running`; on startup, agents still recorded as active are marked interrupted, their tasks return to Ready, and a process left behind is stopped only if its command line is still `claude` with that agent's exact `--session-id`.
- Terminal logs are saved at exit under `userData/terminal-logs` (directory mode 700, files 600) and may contain anything the agent printed, including secrets.


**Known limits of the agent runtime (read these)**
1. **A person typing in the terminal is not restricted.** Claude Code's `!` shell mode ran a command in a planning-stage session even with `Bash` denied (tested: a file was created). The deny rules constrain the model, not the keyboard. Because the terminal passes keystrokes through, anything able to call `agents:write` can run shell commands as the user, in a PTY whose cwd is the worktree but which is not confined to it. This is inherent to an interactive terminal (a product requirement). Planning agents now have a best-effort input guard (`input-guard.ts`): `agents:write` refuses input that would put `!` at the start of an empty prompt line (`SHELL_MODE_BLOCKED`, shown in the terminal). It infers the line state from the keystrokes it forwarded, so it is not a boundary: it cannot see Claude Code's real prompt, other routes exist (for example approving a Bash request the model makes), and **execution agents are not guarded** (a person may need to run commands there). It was not checked against the real CLI's shell-mode trigger. Other mitigations are indirect: the sandboxed renderer, strict CSP, plain-text rendering of untrusted content, and the IPC sender check. There is no technical block.
2. **Worktree isolation is directory isolation, not a sandbox.** The agent runs with the user's privileges. Worktrees share the repository's object store, and creating one adds an `orbyte/*` branch and metadata under the repository's `.git`, which modifies the user's repository (removed again on discard, except a branch that has commits).
3. **Claude's own trust prompt** ("Is this a project you trust?", default "No, exit") appeared in a fresh worktree path and must be answered in the terminal. It did not appear on a later run (possibly because trust carries over from an earlier worktree of the same repository; not verified). Orbyte never writes to `~/.claude.json`.
4. When a project is **trusted**, the agent loads the repo's own settings (hooks included) from the worktree, with the same trust gate and caveats as the Team Lead.
5. **Children and flow control (not verified or not done):** stopping signals the `claude` process, not its process group, so subprocesses it started (MCP servers, `!` shell commands) may outlive it; PTY close normally hangs them up but this was not verified. There is no backpressure on terminal output, so a flood grows xterm's write queue. xterm's link handler could turn an OSC 8 hyperlink in terminal output into an external-URL open; whether the renderer restricts it was not checked. `git worktree` handling needs git 2.30 or later (`--end-of-options`); older git reports a misleading "no commit" error. A replayed history no longer causes xterm to type its replies into the live session (input is ignored until replay finishes).
6. **Crash behavior:** a hard kill (SIGKILL) of the Electron main process also ended the agent's `claude` process (tested), so no orphan was observed. The orphan reaper is defense in depth and is unit-tested only. The terminal buffer is saved at exit, so a crash loses it (the history of an interrupted agent is empty).
7. "Current activity" is the terminal title the program sets (for example "✳ Greet function in greet.js"); it is untrusted text shown as plain text, with control characters, bidirectional overrides and zero-width characters stripped.
8. No plan is captured yet, so an agent that ends sends its task back to Ready. Execution is not possible: nothing supplies `approvalVerified`.

## Logging, recovery and maintenance (Phase 7)
- **Logs stay in main.** `userData/logs/orbyte.log` (directory 700, file 600), rotated at 2 MB keeping three older files. Every line passes through redaction: `sk-ant-` keys, bearer tokens, and `*KEY|TOKEN|SECRET|PASSWORD=` assignments are replaced, and the home directory is shortened to `~`. The logger never throws. Nothing from the logs is sent to the renderer, which still receives only fixed error messages. Redaction is pattern-based, so a secret in an unusual shape could still appear: do not paste logs publicly without reading them.
- **Startup sweep:** after interrupted agents and runs are reconciled, inbox directories whose agent no longer exists are removed and orphan worktrees are counted; one `recovery.completed` event records the result.
- **Orphan cleanup is user-triggered and bounded.** It only looks inside `userData/worktrees/<projectId>/<agentId>`, never takes a path from the renderer (opaque ids matched against a fresh scan), requires the path to be inside the worktree root after following symlinks, refuses a project that no longer exists, and never removes a worktree with uncommitted changes (`git worktree remove` without force).
- **Database backup:** the save location is chosen in a native dialog in main; the copy uses SQLite's online backup API (consistent while the app runs) and is written with mode 600. It contains everything in the database (plans, results, chat history), so store it as carefully as the original.
- **Phase 7 review findings fixed** (a read-only reviewer found nothing critical or high): the logger can no longer throw (formatting, `homedir()` and a closed stdout are all guarded, so the `uncaughtException` handler cannot loop); entries are sanitized (control characters and ANSI escapes escaped, continuation lines indented so text cannot forge an entry, 8 KB cap, byte-accurate rotation); redaction now covers lowercase and camelCase names, JSON-style keys, `Basic` auth, `--api-key` flags and common token shapes (GitHub, `sk-`, AWS key ids, JWTs); the startup sweep finishes before any handler is registered (a new agent's inbox cannot be swept); orphan cleanup also keeps a worktree whose HEAD has commits on no branch and checks status with user and system git config off; `startExecution` re-checks "being discarded" after its await; the backup file is created private (mode 600) before data is written, and only one backup dialog runs at a time.
- **Phase 7 review, recorded not fixed (Limitation):** a result review is not re-bound to the snapshot at the moment it is stored (acceptance still compares a fresh snapshot, so it fails closed); a review skipped because the worktree changed shows only as "not reviewed" in the UI; redaction is pattern-based and a differently shaped secret could still be logged, so the policy is to log `err.message` rather than whole error objects from process or SDK calls where practical; `agents:discard` accepts `force` from the renderer (pre-existing, user-intended); ignored files such as a gitignored `.env` do not stop a worktree removal (same as `discard`).
- **Two Phase 6 gaps closed:** a Team Lead result review is only started when the worktree still matches the submitted snapshot; `discard` marks the worktree as being discarded (refusing a concurrent execution start) and re-checks for a live agent or active task right before deleting.

## Execution, results and completion (Phase 6)
- **Starting is gated in main.** `executions:start` carries only project and task ids. `ExecutionService.start` calls `ApprovalService.verify`, stops the planning agent (two agents never share a worktree live), then `authorizeExecution`, which spends the approval (one-shot) before the process starts. A failed launch fails closed: the task returns to `awaiting_approval` and needs a fresh approval. A run that ends without a result does the same.
- **Execution launch** (`launch.ts`): `--permission-mode acceptEdits`, `--tools=Read,Glob,Grep,Edit,Write,Bash`, `--strict-mcp-config` with only Orbyte's server, `--allowedTools` limited to `git status|diff|log` reads and Orbyte's two report tools, denied `NotebookEdit, WebFetch, WebSearch, Task`, no bypass flags, same env allowlist. Verified against the real CLI: file edits run unattended, allowlisted git reads run, interpreter commands (for example `python3 -c`) stop at a prompt in the terminal for you to answer. The agent is told not to commit or push; that is a prompt, not enforcement. Its changes stay in the worktree and branch for you to merge.
- **The agent's report is a claim.** Progress notes, the result summary and the test list come from the agent and are shown labeled "unverified". Orbyte does not run tests. What Orbyte trusts is evidence it collects itself from git (HEAD, changed files with line counts, commits, a hash over the diff and untracked file contents), with hooks, fsmonitor, external diff and textconv turned off. `executionStatus: succeeded` means a result was produced, not that anything passed.
- **Completion needs three things, re-checked at the moment of acceptance:** a Team Lead review of that exact result (advice only; it is a fresh unsaved session that cannot accept anything), your explicit acceptance of the CURRENT result, and a new git snapshot equal to the one stored with the result (code changed afterward means `CODE_CHANGED`). `CompletionService` is the only code that passes `completionVerified: true` (a test scans for it), and the state machine refuses `completed` from any actor without it. A later result supersedes and invalidates an earlier acceptance.
- **Result freeze:** on `submit_result` the agent is stopped so the reviewed code is the code that stays. Anything that edits the worktree afterward (you, in a terminal) shows up as changed code and blocks acceptance.
- **Change requests are single use.** "Request changes" stores your decision and feedback; `authorizeRevision` (in `approval-service.ts`, so `approvalVerified: true` still lives in one file) spends it to move the task back to `in_progress`. One request authorizes exactly one revision run. The feedback reaches the agent as defanged data inside a fence.
- **Result review by the Team Lead** gets read access to the agent's worktree through `additionalDirectories` (review turns only), the diff in the prompt (capped), and the agent's claims labeled as claims. Results replaced while a review runs discard that review.
- **Discard** is refused while the task is `in_progress` or `in_review` and while any agent sharing the worktree is live.
- **Inbox:** same limits as plans (private dir mode 700, 256 KB, at most 10 files per kind per drain, no symlinks, Zod validation per kind); the server's tool set depends on the kind passed by Orbyte, not the agent.
- **Review findings fixed** (a read-only reviewer examined this phase; it found no way to start or complete a task without your stored decision): (1) the execution launch no longer pre-approves any Bash prefix, because `git diff --output=FILE` and `git diff --no-index` pass a prefix rule and write or read anywhere; (2) evidence collection runs git with inherited `GIT_*` redirects stripped, user and system config off, global attributes off, and refuses a worktree whose `.git` pointer no longer leads outside the worktree (the agent can edit that file); (3) edits to `.claude/**`, `.mcp.json`, `.git` and `.gitattributes` are denied for the agent, and ignored files under `.claude/` and `.mcp.json` are included in the evidence hash; (4) execution launches exactly the plan the spent approval was for (re-read after the gate); (5) a failed evidence collection fails the run closed (task back to the gate) instead of leaving it stuck, and diff/listing buffers are larger with `--` before paths; (6) a result whose evidence was truncated cannot be accepted; (7) `executions:get` shares one git run per task for a few seconds.
- **Reviewed, not fixed (Limitation):** (the review-snapshot and discard-versus-start gaps were closed in Phase 7); a trusted project's settings files can add permission rules (agent edits to `.claude/**` are denied but a command you approve in the terminal could change them); the execution agent inherits `ANTHROPIC_API_KEY` and `CLAUDE_CODE_OAUTH_TOKEN` and has `Bash`, so any command you approve can read them (planning agents had no Bash); the Team Lead's `reject` or `revise` advice does not block acceptance, by design.
- **Limits that remain:** terminal input is unrestricted (the `!` shell mode); the agent runs as your user, so it can read and write anything you can, not just the worktree (directory isolation, not a sandbox); the gate is not an OS-level boundary and approvals and acceptances are signed but a process that can use the key is not stopped (see above); Claude shows its own folder-trust prompt the first time in a new worktree; packaging the agent server and native modules is Phase 7.

## Usage figures
Agent token usage is read from Claude Code's own session files under the Claude config directory (`CLAUDE_CONFIG_DIR` or `~/.claude/projects/<folder>/<session>.jsonl`). What is enforced: the session id comes from Orbyte's own agent record and must look like a UUID; the folder name is derived from the recorded worktree path; the file must be a regular file (links are refused) of at most 100 MB; only the numeric token fields of each message are read, nothing else is kept or sent, and no path reaches the renderer. Limits: the file format is Claude Code's and undocumented, so a CLI update may make agents show as "unreadable"; messages are counted once by id because the file repeats them per content block. Team Lead figures are the SDK's own estimates. Nothing here is billing data.

## Showing the changes
`executions:changes` reads the worktree through `GitWorktrees.changesText` (git with config, external diff and textconv off, `.git` pointer checked). New untracked files come from Orbyte's own snapshot list, and each is still required to be a regular file whose real path is inside the worktree (links, `..`, absolute paths, and files over 256 KB or with binary content are named, not read). Output is capped and shown as plain text. It refuses when the code no longer matches the result. Limits: the text can contain anything the agent wrote, including secrets in the worktree; it is shown only to you, and it is not stored.

## Notifications
Notifications are shown by main only, carry the project name and the title of the proposal, plan or task (your own data, shown by the OS notification center, which may keep a history and show it on a locked screen), and have no actions: clicking only focuses the window. They cannot approve, accept or start anything.

## Orbyte-run tests
A button in the result dialog runs the project's own `scripts.test` (from a regular `package.json` at the worktree root, package manager chosen from the lockfile) in the agent's worktree. What is enforced: the command is found by Orbyte and never comes from the renderer; it is started without a shell, in its own process group, with a 5-minute timeout and a 32 KB output tail; the environment is an allowlist with no Claude, cloud or token variables; it runs only for the current result of a task in review and only if a fresh snapshot equals the result's hash; one run per task at a time; runs left `running` by a crash are marked `error`; processes are killed when Orbyte quits. The outcome is stored with the snapshot hash and labeled as collected by Orbyte. Limits: this executes the agent's code as you, with your files and network, so it is not a sandbox (the UI asks you to confirm); a test script can read anything you can; tests are not required for acceptance and change no task state; a fresh worktree has no installed dependencies, so many suites fail until dependencies are installed there (Orbyte does not install them).

## Plans, reviews and the approval gate (Phase 5)
**Code-enforced**
- **Only your approval creates an approval record.** `plans:approve` (IPC, sender-checked) is the only path to `PlanRepository.addApproval(... 'approved')`. The Team Lead, the agent, the plan file, the MCP server and the renderer cannot create or substitute for one. The record stores task, agent, plan version, plan hash, reviewer (`user`), status and time; the database allows at most one valid approval per task (partial unique index).
- **The Team Lead's review is advice.** It is stored as a recommendation with reasons (`plan_reviews`) and has no code path to an approval (tested, and verified with the real Team Lead: a review recommending "approve" left the gate closed). Reviews run automatically when a plan arrives, in a **fresh one-shot session** that is never saved and never touches the chat session id (verified against the real SDK: no session file was written, the chat session id was unchanged), so hostile text in a plan cannot carry into your later chats. The plan is shown to the reviewer as data with angle brackets defanged so it cannot close its fence.
- **The gate** (`ApprovalService.verify`) re-reads everything instead of trusting cached state: project active, task `awaiting_approval`, a valid unrevoked approval for the CURRENT plan version, the stored hash equal to the recomputed hash of the plan content, reviewer `user`, all dependencies completed, and the plan's agent still existing with its worktree intact. `authorizeExecution` is the only code in the application that passes `approvalVerified: true` to the task state machine (a test scans the source for it). It is not reachable from the renderer directly; `executions:start` runs it in main.
- **Approvals are one-shot and strictly scoped.** `authorizeExecution` spends the approval before moving the task, so a later return to Ready cannot reuse it; a changed plan is a new numbered version and invalidates any approval atomically, and an old version can never be approved; an approval cannot be revoked once execution began; moving a task out of awaiting approval (blocked, cancelled, back to Ready) drops its approval; every plan, review and approval call checks the project id (another project gets the same `NOT_FOUND` as a missing record).
- **Plan capture:** the agent's only extra tool is Orbyte's `submit_plan`, served by a tiny stdio MCP server that writes a Zod-validated plan to the agent's private inbox (mode 700, enforced with chmod). Orbyte drains it: files are size-limited (256 KB), at most 10 per drain, symlinks and non-files are never followed, names must match `plan-*.json`, invalid files are discarded, the agent cannot choose a path, at most 20 plan versions per task. A plan submitted just before the agent exits is not lost (the exit waits for any in-flight read and drains again). A plan only counts for a task that is being planned.
- **Launch:** still `--tools=Read,Glob,Grep` plus `--strict-mcp-config`; the only MCP server is Orbyte's (the wildcard deny `mcp__*` was removed from the planning launch because it would also block it). Tested: exactly one server configured, its environment, and the inbox path.
- **`submit_plan` is declared `readOnlyHint: true`** so plan mode does not stop at a permission prompt (Orbyte must not answer prompts for you). The hint is a client-trusted claim; it is accurate in practice because the tool writes only to Orbyte's private inbox and never touches the repository. Do not copy the pattern to any tool that does.

**Not enforced / known limits**
- **Signed approvals (migration 0008).** Approvals (`plan_approvals`) and your decisions (`result_decisions`: acceptances and change requests) carry an HMAC-SHA256 `signature` over their authorizing fields, including the invalidation state (a spent or invalidated row is re-signed). The key is 32 random bytes in `userData/signing.key`, encrypted with Electron `safeStorage` (macOS Keychain). `validApproval`, `validAcceptance` and `validChangeRequest` ignore any row whose signature does not verify, so editing a row, inserting one, clearing an invalidation or a row from before signing authorizes nothing (tested). If the OS cannot protect the key, Orbyte refuses to record approvals (`SIGNING_UNAVAILABLE`) instead of storing a plaintext key.
- **What signing does not stop.** A process running as you that can use the same protected key (it may trigger a Keychain prompt, but could be answered by you or bypassed on a weaker platform), or that replays an older signed copy of a row (for example a backup of the database to bring back a spent approval), is not stopped. Plan rows and the plan hash are not themselves signed: the approval signs the plan hash, so a swapped plan fails the hash check. Existing unsigned approvals from before this change no longer authorize anything; approve again. So the gate is still not an OS-level boundary against a determined local process, but a plain database edit no longer forges an approval or acceptance.
- A plan is free text from the agent. The user reads and decides; Orbyte does not judge its quality. The Team Lead's recommendation can be wrong or steered by the plan text (the UI labels it as advice; approving against a "revise/reject" recommendation asks you to confirm).
- Ingest does not check that the submitting agent is still live (only live agents are drained today), and a failed move to `awaiting_approval` is only logged. A review that cannot run (Team Lead busy for too long, auth failure) is logged, not shown. These are accepted for now.
- `submit_plan` has no rate limit of its own beyond the per-drain and per-task caps above.
- The plan server needs `ELECTRON_RUN_AS_NODE` and the built `out/main/plan-server.js` plus `node_modules` beside it; packaging ships it inside `app.asar` and runs it through Electron's Node mode (checked in a local x64 build: it answered `tools/list`).

## Phase 3 limitations
- A task's dependencies are not enforced at "ready"; `ready` means the user authorized it. Dependency completion must be enforced when a developer agent starts (Phase 4).
- Cancelling a task has no process to stop yet; once agents exist, cancel must also stop the agent (Phase 4).
- Task titles and descriptions come from the Team Lead or the user and are rendered as plain text. They may be shown back to the model through `list_tasks`, so treat them as untrusted input there too.
- The Team Lead may still propose duplicate or unwanted tasks; the guard is that the user must approve, not that proposals are always good. Whether the model proposes only when asked is prompt guidance, observed in one real run, not enforced.

## Phase 3 review findings (read-only reviewer; no critical or high)
Fixed: repeated dependency keys made a proposal that could never be approved and wasted a pending slot (now rejected by schema and service, with a combined 20-dependency cap); the edit dialog could trap a task whose dependency was later cancelled; the Team Lead only saw the oldest 100 tasks (now open and newest first, with the true total and a truncation flag); the review card hid which existing tasks a proposed task depends on (titles now shown); `list_tasks` could throw into the SDK (now a tool error).

Open, accepted for now:
- **Provenance is not proof (low).** `approve` takes item content from the renderer and only checks keys against the stored proposal, so `source: team_lead` does not prove what the model wrote. A compromised renderer could already use `TaskService.create`, so this is provenance, not privilege. Consider comparing with the stored items and recording an "edited" flag.
- **Review-queue flooding (low).** Caps are 3 `propose_tasks` calls per turn and 5 pending proposals. A runaway or injected model can fill the queue until the user dismisses proposals. "Only propose when asked" is prompt text, not enforcement; the real controls are human approval and these caps.
- **Unbounded listings (low).** `proposals:list` returns all historic proposals; very large backlogs could hit SQLite's variable limit in `inArray`. Paginate and chunk if backlogs grow.
- **`approvalVerified` is a caller-supplied boolean.** Unreachable today. Phase 5 must look up a stored approval record for the current plan version instead of trusting a flag.
- **Phase 4/5 follow-ups:** moving `in_progress` to cancelled or blocked must stop the running process; `ready` does not require completed dependencies (enforce when an agent starts); approval and execution columns are not reset on reopen.
- **Hardening:** `TaskService.update` checks status then writes without a status guard; it is safe only while synchronous, so add a status condition to the UPDATE if an `await` is ever introduced.

## Required for later phases (Planned; not built, not enforced)

- Keep treating repository content, plans and agent output as untrusted when rendering or when building prompts.

## Update check
`modules/updates/update-service.ts` reads `https://api.github.com/repos/aqeel-dm/orbyte/releases` (fixed URL, from main, no credentials, nothing about you sent) and shows "Update to vX" when a newer `vMAJOR.MINOR.PATCH` release exists. The release page URL must start with `https://github.com/aqeel-dm/orbyte/releases/`; `updates:openDownload` takes no argument and opens only that stored URL with `shell.openExternal` (a new `openExternal` path, deliberately limited to this). Nothing is downloaded or installed by the app, so a bad release page cannot run code by itself. Limits: the downloaded app is **unsigned**, so you rely on GitHub and the release's `SHA256SUMS.txt`; checks need the repository (or a releases-only repository) to be public; there is no off switch. Silent in-app update is **Planned** (needs signing and notarization).
